# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.0.5] - 2026-09-13

Answers the security advisory coverage review, first the two points of
[comment #6](https://www.drupal.org/project/projectapplications/issues/3618652#comment-16744839)
and then the login findings of
[comment #13](https://www.drupal.org/project/projectapplications/issues/3618652#comment-16768977).

### Security

- The per-user login counter is keyed on the account id instead of the name as
  typed. The `identifier` column of the flood table is ASCII, so a name such as
  Zoë made `isAllowed()` throw on MySQL and MariaDB and cost that account a 500
  with the right password; the same column compares case-sensitively on
  PostgreSQL and SQLite, where user names do not, so `Admin` and `admin` reached
  one account through two counters. This is what core's
  `UserAuthenticationController::getLoginFloodIdentifier()` does. Core stops
  there and gives an unknown name no counter at all, which turns the 429 into an
  enumeration oracle; these endpoints answer the same way for every name, so an
  unknown one is keyed on a case-folded hash of it.
- The hash the login verifies against for an unknown user is generated by the
  site's own password service and kept in state, rather than being a constant.
  The constant was bcrypt cost 10, while PHP hashes at cost 12 from 8.4:
  verifying against it returned in roughly a quarter of the time a real check
  took, which told a known name from an unknown one by latency — the opposite of
  what it was there for. It is regenerated whenever the password service reports
  it outdated, so it follows the site's settings from then on.
- A successful login re-hashes a password whose stored hash is outdated, as
  core's login does. Without it, a user who only ever signs in through
  `/auth/token` kept the hash their account was created with through any later
  change of algorithm or cost. The account save this performs is flagged so that
  `hook_user_update()` does not read it as a new password and revoke the
  account's other refresh tokens: re-encoding a password is not a credential
  change, and the day a site changes its hashing settings should not log
  everyone out of their other devices.

### Changed

- The settings form carries its bounds as `#min` and `#max` on the number
  elements, which validate themselves and expose the range in the markup, so
  `validateForm()` is gone. The two lifetimes had no lower bound at all and a
  negative one was saved; they are now 60 to 86400 seconds for the access token
  and 300 to 2592000 for the refresh token. Stored configuration is not touched
  and no update hook runs, but a site that had set a lifetime below those floors
  will have to raise it the next time it saves the form.
- Hooks are class methods now. `hook_cron()`, `hook_user_update()`,
  `hook_user_cancel()` and `hook_user_delete()` live in
  `Drupal\jwt_token_refresh\Hook\JwtTokenRefreshHooks`, and
  `hook_runtime_requirements()` in `JwtTokenRefreshRequirements` — the same
  layout core uses. Attribute-based hooks are only discovered from Drupal
  11.1, so the procedural implementations stay for 10.3 to 11.0; each is a
  one-line call into those classes and carries `#[LegacyHook]`, so a core that
  understands both runs the class once rather than both twice. Checked on
  11.4: exactly one registered implementation per hook. The one requirements
  hook that has to stay procedural is `hook_requirements()`, which no core
  supporting attributes still calls.
- The settings form maps its elements onto configuration with
  `#config_target` and no longer has a submit handler; the parent class both
  loads and saves. Every target casts on the way in, because a number element
  submits a string and a checkbox an integer, and the schema promises an
  integer and a boolean. The form test now asserts the stored types strictly,
  including a checkbox in each direction.

### Fixed

- The comment recording why the core floor is 10.3 claimed that widening it to
  `^10` would be a one-line change. That was true when written and is not any
  more: `#config_target` arrived in 10.2, so the settings form is now the one
  thing that would not run on 10.0 or 10.1.
- Comments that described code as it no longer is: the class docblock of
  `RefreshTokenManager`, which still announced the access token cascade as a
  later phase after the service had grown it; the `@file` summary of the
  `.module`, now the single line moderators ask for, with the rationale it
  repeated left in the class it belongs to; a rollback comment in
  `TokenController::issue()` and a pipeline number in `.gitlab-ci.yml`, both of
  which belonged in a commit message.

## [1.0.4] - 2026-08-23

Documentation only, plus one contextual help text. No code path changes, no
configuration changes.

### Added

- The settings form now explains, beside the *Inject a refresh token into
  /user/login* checkbox, how it interacts with `jwt_auth_issuer`'s own *Include
  a JWT token in the user login response* — and links to that page. The
  neighboring box ships **enabled**, and that submodule has no concept of
  refresh, so the shipped default puts an access token in core's login response
  that nothing can renew: it behaves like a working login until it expires. Of
  the four combinations only that one is a trap, so the advice is to uncheck it
  unless core's login route is used deliberately, and to enable this module's
  injection if it is. Deliberately not surfaced on the status report: with both
  settings at their defaults, such a warning would fire on every fresh install,
  including the many sites that never call `/user/login`.

### Fixed

- The quick start described a *Generate a key* button that does not exist for a
  JWT key. The input widget is not the user's choice — `KeyFormBase` derives it
  from the key type, and `JwtHsKeyType` pins it to a plain text field — so the
  reader has to bring their own secret. Two further details were wrong: the
  field is titled *JWT Algorithm* and appears only once the key type is chosen,
  and there are two distinct *Base64-encoded* checkboxes, one encoding the
  secret at rest and one declaring that what you paste is already base64.
  Ticking the wrong one yields a key that validates and then fails to sign.
- en-US spelling for a checkbox state, which is also the wording Drupal's own
  form API uses.

## [1.0.3] - 2026-08-23

### Fixed

- The log entry naming *why* token issuance failed was written inside the
  transaction that the failure then rolls back, so it was discarded along with
  it. The only surviving entry said `JWT generation failed; rolled back.`,
  which told an integrator nothing. Found by installing 1.0.2 from
  drupal.org into a fresh Drupal 11 site: a missing signing key gives a bare
  `500 internal_error` and, until now, a log with no cause in it. The reason is
  now logged after the rollback, and names the missing key when the issuer
  simply returned nothing. The HTTP response is unchanged, deliberately: an
  anonymous caller has no business learning about server misconfiguration.

### Changed

- The README leads with a six-step quick start that was executed end to end on
  a fresh site, including the scripted key creation, rather than "configure a
  key in jwt and you are done". Two behaviors newcomers were mistaking for
  bugs are now stated up front: a default logout leaves the access token valid
  until it expires, and five failed logins lock an account for six hours.

## [1.0.2] - 2026-08-23

### Fixed

- A successful login through the core `/user/login?_format=json` route could
  answer `500` instead of `200` when no usable JWT signing key was configured.
  `UserLoginInterceptSubscriber` called `JwtAuth::generateToken()` unguarded,
  and `drupal/jwt` raises an `Error` from its transcoder in that state
  ([#3409096](https://www.drupal.org/project/jwt/issues/3409096)). Core has
  already authenticated the account by the time this subscriber runs, so the
  response is now left exactly as core built it and the failure is logged
  instead. `POST /auth/token` already guarded this path.
- Both call sites tested `generateToken()` against `FALSE`, following its
  docblock. It actually returns the transcoder's `?string`, so a missing key
  yields `NULL` and the check never fired. They now reject any non-string,
  which keeps the typed `500 internal_error` on `/auth/token` correct once
  the upstream fatal is fixed.

## [1.0.1] - 2026-08-22

### Added

- A status report entry for the JWT signing key. Without one the module cannot
  issue or validate anything, and the failure surfaced only on the first API
  call — as a 500 raised inside `drupal/jwt`, not as a typed error. The status
  report now says so, with links to the two pages needed to fix it.

### Fixed

- `POST /auth/token/revoke` answered an HTML access-denied page when the
  request carried no `Authorization` header, breaking the promise that every
  error is a JSON envelope with a stable code. It now returns
  `401 invalid_token` with a `WWW-Authenticate: Bearer` header. A credential
  that *is* presented is still left alone: an opaque Bearer token may belong
  to another authentication provider, and this module does not claim it.

## [1.0.0] - 2026-08-22

Initial public release. Everything below is what this first tag contains; there
is no prior published version to compare against.

### Added

- **Login endpoint** `POST /auth/token` — exchanges credentials for an access
  token and a refresh token.
- **Refresh endpoint** `POST /auth/token/refresh` — rotation: every refresh
  issues a new pair and kills the old refresh token.
- **Revoke endpoint** `POST /auth/token/revoke` — Bearer-only logout, `204` and
  idempotent, one token or all of the caller's.
- **Refresh token rotation with OWASP reuse detection** — tokens descending
  from one login share a family id; replaying an already-rotated token revokes
  the whole family. Rotation is an atomic conditional `UPDATE`, which doubles
  as the concurrency lock.
- **Opt-in server-side access token revocation** (`jti` allowlist) making
  logout immediate instead of waiting for the JWT `exp`. Off by default: with
  the flag off, nothing is stored and there is no per-request cost.
- **Per-device logout** — `getRefreshTokenIdForJti()` + `revokeById()` let an
  application sign out the current device only.
- **Account-lifecycle revocation** — a password change, a block, a cancellation
  or a deletion revokes the account's refresh tokens.
- **Response events** `LOGIN_RESPONSE` and `REFRESH_RESPONSE` so application
  modules can enrich the token payload without patching this module. See
  `jwt_token_refresh.api.php`.
- **Opt-in `/user/login` injection** — adds a `refresh_token` to the core JSON
  login endpoint so an existing frontend can keep using it.
- **Admin settings form** at `/admin/config/system/jwt-token-refresh`: token
  lifetimes, refresh token entropy (32-byte floor, clamped in code), per-user
  token cap, flood limits, cron cleanup, revocation toggle and `jti` entropy.
- **Stable machine-readable error codes** on every failure response
  (`invalid_credentials`, `invalid_token`, `token_expired`, `session_revoked`,
  `too_many_attempts`, `validation_failed`, `internal_error`).
- **Flood control** on login and refresh, per IP and per user/IP.
- Test coverage: 26 kernel tests and 24 functional tests.

### Security

- Refresh tokens and `jti` values are generated with a CSPRNG and stored as
  SHA256 hashes only; raw values are returned to the client once and never
  persisted.
- Failed logins are constant-time and indistinguishable from one another
  (anti-enumeration): unknown user, wrong password and blocked account all
  return the same `401 invalid_credentials`.
- Token responses carry `Cache-Control: no-store`.
- The dedicated log channel records security events without raw tokens.

See [SECURITY.md](SECURITY.md) for the full threat model and trade-offs.
